# Implementation Plan: Read Zarr v3 (core + sharding) keeping the v2 API

**Branch**: `006-zarr-v3-reader` | **Date**: 2026-07-09 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `/specs/006-zarr-v3-reader/spec.md`

## Summary

Add read support for Zarr v3 (single `zarr.json` per node, `node_type` discriminator, named
data types, an ordered codec chain, `chunk_key_encoding`, v3 fill values, the `sharding_indexed`
codec with byte-range inner-chunk reads, and v3 consolidated metadata) **behind the unchanged
public API** (`open`/`openArray`/`openGroup` → `ZarrArray`/`ZarrGroup`, same `get(selection)`),
with **automatic v2-vs-v3 detection** and **no regression on v2**.

Technical approach: introduce a **version-neutral resolved-metadata type** that both the existing
v2 parser and a new v3 parser produce, so the entire downstream read path (`ZarrArray`,
`loadChunks`, caches, stores, limiter, decode pool) is shared and mostly unchanged. Generalize
the single decode-only `Codec` into an ordered **`CodecPipeline`** (array→array, exactly one
array→bytes, bytes→bytes; decode in reverse) that also fixes the current gap where v2 `filters`
are parsed but never applied. Centralize metadata-key construction and array/group detection
behind a small **layout** abstraction so `zarr.json` vs `.zarray`/`.zgroup` is resolved in one
place. Implement `sharding_indexed` as a codec that reads the shard index and fetches inner-chunks
by `getRange`, coalescing adjacent ranges under a configurable gap threshold, falling back to
whole-shard reads when `getRange` is absent. Reuse all existing performance infrastructure
(decode pool, byte-budgeted caches, `ByteLimiter`, concurrency-limited fan-out) unchanged.

## Technical Context

**Language/Version**: TypeScript 5.x, `strict: true`, ES2022, ESM-only
**Primary Dependencies**: `numcodecs` (Blosc, incl. zstd via Blosc; runtime), `@aws-sdk/client-s3`
(optional peer), `ioredis` (optional peer); Node built-ins `node:fs/promises`, `node:crypto`,
`node:path`, `node:zlib`, native `fetch`. New: a `crc32c` implementation (small dependency or
in-repo table-based implementation — decided in research).
**Storage**: Local filesystem (disk chunk cache), remote stores (FS/HTTP/S3/Reference), optional
Redis (shared metadata cache). No new backends.
**Testing**: Existing test runner + shared contract suites (`tests/contract/store.contract.ts`,
`cache.contract.ts`); integration harness `FileSystemStore + openArray + expected.json`
(version-agnostic in shape). Fixtures generated by reference Python `zarr` v3
(`tests/fixtures/generate.py`, extended with `zarr_format=3` paths incl. a `sharding_indexed`
fixture).
**Target Platform**: Node.js >= 22 (LTS), server-side. No browser.
**Project Type**: Single TypeScript library (`src/` + `tests/`).
**Performance Goals**: v3 core read is performance-neutral vs v2 (1 chunk = 1 object). Sharded read
of a sub-region on a `getRange`-capable store issues byte-range reads per touched inner-chunk with
zero full-shard downloads. No invented throughput target; measured locally on large/sharded
fixtures.
**Constraints**: Public API signatures unchanged (FR-002, Principle VI); all existing v2 fixtures
and tests pass unchanged (FR-020); reuse existing decode pool / caches / limiter / fan-out
(FR-018); `getRange` used only via the existing optional Store capability (FR-017).
**Scale/Scope**: Reader over arrays up to multi-GB (existing `large_100mb`/`large_1gb` fixtures;
new v3 + sharded equivalents). Supported dtype set fixed by FR-004.

| V. Server-First Performance | PASS | Reuses `DecodePool`, `MemoryCache`/disk cache, `ByteLimiter`, `loadChunks` fan-out. Sharding uses native ranged reads. Benchmarks on large/sharded fixtures tracked. |

| VII. Simplicity (YAGNI) | PASS | The two new abstractions (neutral metadata, `CodecPipeline`) are each demanded by a concrete v3 scenario (dual-format detection; ordered chain), not speculation. Sharding fallback avoids speculative range logic. No Complexity Tracking entry needed. |

```text
src/
├── metadata/
│   ├── types.ts          # + version-neutral ResolvedArrayMeta / ResolvedGroupMeta
│   ├── v2.ts             # unchanged parse; adapter to neutral type
│   ├── v3.ts             # NEW: parse zarr.json (array/group), codec chain, fill_value, chunk_grid
│   ├── layout.ts         # NEW: metadata-key + detection abstraction (zarr.json vs .zarray/.zgroup)
│   ├── consolidated.ts   # v2 consolidated (unchanged)
│   └── consolidated-v3.ts# NEW: v3 consolidated_metadata (nested) reader
├── codec/
│   ├── codec.ts          # + CodecPipeline type; registry extended
│   ├── pipeline.ts       # NEW: ordered pipeline (array→array / array→bytes / bytes→bytes), reverse decode
│   ├── bytes.ts          # NEW: v3 bytes/endian codec (array→bytes)
│   ├── transpose.ts      # NEW: v3 transpose codec (array→array)
│   ├── crc32c.ts         # NEW: v3 crc32c checksum codec (bytes→bytes, verify+error)
│   ├── sharding.ts       # NEW: sharding_indexed codec (shard index + byte-range inner chunks)
│   ├── gzip.ts, raw.ts, decode-pool.ts, decode-worker.ts  # reused
├── chunk/
│   ├── indexing.ts       # + v3 chunk_key_encoding (default 'c' prefix, configurable sep; 'v2' encoding)
│   ├── loader.ts         # generalize single Codec → CodecPipeline in LoadChunksContext
│   └── limiter.ts        # reused
├── dtype.ts              # + v3 named data_type map (float16→Float32Array, int64/uint64→BigInt)
├── array.ts              # consume neutral meta + pipeline; chunk-key via layout/indexing
├── group.ts              # child detection/keys via layout
├── open.ts               # detection via layout; build pipeline from neutral meta
└── (store/, cache/, dataset/, spatial/, redis/ unchanged)

tests/
├── unit/                 # + v3.metadata, pipeline, bytes/transpose/crc32c codecs, sharding, dtype-v3, layout, chunk-key-v3
├── integration/          # + v3 array/group, v3 sharded byte-range, v3 consolidated
├── contract/             # store.contract.ts exercises getRange (already present)
└── fixtures/
    ├── generate.py       # + zarr_format=3 generators incl. sharding_indexed fixture
    └── <new v3 fixture dirs>  # zarr.json + c/… chunk keys + expected.json (reused schema)
```

**Structure Decision**: Single-project TypeScript library (existing layout). New v3 code is added
as sibling modules under `src/metadata`, `src/codec`, and `src/chunk`, feeding the existing
`ZarrArray`/`ZarrGroup`/`loadChunks` read path via a version-neutral resolved-metadata type. No
new top-level directories; the store/cache/dataset/performance layers are reused unchanged.
